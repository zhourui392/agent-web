# Harness 界面设计建议（v2）

> 基于 MVP 实现（`admin/harness.html` + `js/admin/pages/harness.js` + `css/admin.css`）的界面审视，按优先级从高到低排列。
> 审查时间：2026-07-24
> 对应版本：M4 纵向切片完成，Feature Flag `agent.harness.enabled` 默认开启
> 页面结构：左侧 Run 列表（270px）+ 右侧详情区（Summary Card → 四阶段卡片 → 阶段详情 Card）

---

## 总体评价

当前 MVP 实现的**功能密度很高，审计信息很完整**——四个阶段、能力快照、Gate、Approval、部署、时间线、补充问题全部可见且可操作。
但作为一个"受控交付控制面"，**信息层级和视觉引导还可以优化**：

1. **主流程与审计操作混在同一层级**：对话协作区（用户 80% 时间在这里）和 5 个 Tab 的高级表单挤在同一张 Card 里，目光不断被下方表单干扰
2. **操作入口重复且分散**：批准/拒绝/Gate 执行同时出现在对话区底部和「Artifact 与 Gate」Tab，用户困惑哪个是"正确入口"
3. **四阶段卡片缺少流程感**：平铺的 4 个按钮表达不出顺序依赖和 INVALIDATED 的因果关系
4. **能力表单看起来可编辑但实际是审计信息**：「执行与能力」Tab 里一大片 input 框，用户会以为可以改能力配置，实际上大多数只是展示 Snapshot 解析结果

> 💡 设计目标收敛为一句话：**让"和 Codex 协作改需求 → 校验 → 批准进入下一阶段"这条主路径一眼能走完，审计信息完整但不抢焦点。**

## 🔴 高优先级（P0）

### 1. 阶段详情拆为「工作区 + 审计抽屉」两层

**现状问题**：
- 对话区和 5 个 Tab 挤在同一张 `harness-stage-detail` Card 里，滚动时对话和表单互相遮挡
- 「Artifact 与 Gate」Tab 顶部有 4 个操作按钮（执行 Gate / 请求批准 / 批准 / 拒绝），对话区底部也有 3 个几乎一样的按钮（校验并请求批准 / 批准 / 拒绝），入口重复
- 「执行与能力」Tab 的表单（Skill ID、MCP ID、文件根目录等共 10 个 input）看起来可编辑，但大部分只是 Snapshot 解析时的输入展示——真正的写操作只有底部 2 个按钮（固化 Snapshot / 启动 Runtime），却被埋在表单最下方

**建议方案**：

阶段详情 Card 拆成上下两个区域：

```
┌─────────────────────────────────────────────────────────┐
│  阶段头部（名称 / Attempt / 状态 / 启动·重试·登记问题）    │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  【工作区】对话协作 + 主操作（占据主要视觉空间）            │
│  ┌───────────────────────────────────────────────────┐  │
│  │  与 Codex 协作                                      │  │
│  │  ... 消息列表 ...                                    │  │
│  │  输入框 + 发送按钮                                    │  │
│  │  ─────────────────                              │  │
│  │  主操作区（校验并请求批准 / 批准 / 拒绝）             │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
│  ▼ 查看审计与高级操作（默认收起，点击展开 / Drawer）       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**具体改动**：
- 5 个 Tab **从主 Card 移到抽屉/折叠面板**，默认收起，标题改为「查看审计详情」
- Tab 从 5 个合并为 3 个，按用户心智重新分组：

| 现有 Tab | 合并后 | 包含内容 | 备注 |
|----------|--------|----------|------|
| 执行与能力 | **能力快照** | Snapshot 表格 + Runtime 信息 + 固化/启动按钮 | 表单从"可编辑感"改为"只读展示 + 操作按钮"样式 |
| Artifact 与 Gate | **产物与审批** | Artifact 版本历史 + Gate 结果 + Approval 历史 | 移除 Tab 内的批准/拒绝按钮，只留列表 |
| 补充输入 + 部署 + 时间线 | **审计追踪** | 补充问题（含回答操作）+ 部署执行 + 事件时间线 | 部署操作保留，因为它是 DEPLOYMENT 阶段的主动作 |

- **主操作按钮只留一份**在对话区底部：
  - 启动阶段 / 重试 → 阶段头部（始终可见）
  - 校验并请求批准 / 批准 / 拒绝 → 对话区底部（`harness-conversation-next` 区域，强化为主要决策点）
  - 执行 Gate → 合并进「校验并请求批准」按钮的次级菜单，或移到抽屉里
- 「执行与能力」Tab 的 10 个 input 框**改成只读描述列表样式**（`el-descriptions` 或 label + 文本），底部的 2 个操作按钮保留并上移到该 Tab 顶部

**涉及文件**：`admin/harness.html`（结构重排）、`css/admin.css`（新增折叠面板 / Drawer 样式）、`js/admin/pages/harness.js`（按钮可见性逻辑调整）

**改动量**：中（结构改动较大，但不涉及后端 API）

**价值**：信息架构层面的关键优化——主流程视线从"对话 + 5 个 Tab + 一堆按钮"收敛为"对话 + 底部决策"，新用户认知负荷降低 60% 以上。

### 2. 四阶段卡片改为带流程感的 Stepper

**现状问题**：
- 四阶段是平铺的 4 个 `.harness-stage-card` 按钮（grid 4 列），只有序号 + 名称 + 状态 Tag + Attempt 号
- 缺少「流程感」：用户不容易一眼看出当前推进到哪一步
- INVALIDATED 状态的因果关系不直观：上游变了导致下游失效，用文字 Tag 表达不出来
- 状态只用 `el-tag` 文字表达，视觉区分度不够（`stageMeta()` 只映射了 type 颜色）

**建议方案**：

改成**带连接线的步骤条（Stepper）**样式：

```
  ┌─────┐    ┌─────┐    ┌────────┐    ┌──────┐
  │  ●  │───▶│  ◷  │───▶│   ○    │───▶│  ○   │
  │需求分析│    │方案设计│    │ TDD 实现 │    │部署验证│
  │ ✓ 通过 │    │ 待审批 │    │ 未开始  │    │ 未开始 │
  │ 3 条 AC│    │Attempt 2│    │        │      │
  └─────┘    └─────┘    └────────┘    └──────┘
```

**状态视觉映射**：

| 状态 | 图标 | 颜色 | 连接线 |
|------|------|------|--------|
| PASSED | ✓ 实心圆 | 绿 | 实线 |
| RUNNING | ● 动画圆点 | 蓝 | 实线（上游） |
| WAITING_APPROVAL | ◷ 四分之三圆 | 橙 | 实线（上游） |
| WAITING_INPUT | ? 圆 | 黄 | 实线（上游） |
| FAILED | ✗ 实心圆 | 红 | 实线 |
| INVALIDATED | ╱ 斜杠圆 | 灰 | **虚线**（表示失效） |
| PENDING | ○ 空心圆 | 灰 | 虚线 |

**阶段卡片上直接显示关键产物摘要**（替换掉 Attempt 号的位置，Attempt 号移到 tooltip 或次要位置）：
- ANALYSIS 通过后："3 条 AC"（从 REQUIREMENT Artifact 解析）
- DESIGN 通过后："5 个变更点"（从 DESIGN_DOC Artifact 解析）
- IMPLEMENTATION 通过后："8 文件 / 12 测试"（从 IMPLEMENTATION_SUMMARY Artifact 解析）
- DEPLOYMENT 通过后："部署成功"
- 未通过的阶段：显示状态文字或 Attempt 号

**INVALIDATED 的可视化**：
- 下游 INVALIDATED 阶段与上游之间的连接线用**灰色虚线 + 单向叉号**表示断链
- hover 时 tooltip 显示"上游 ANALYSIS 已重新批准，本阶段产物已失效"

**涉及文件**：`admin/harness.html`（阶段卡片模板重写）、`css/admin.css`（Stepper 样式 + 状态图标）、`js/admin/pages/harness.js`（新增产物摘要计算逻辑）

**改动量**：中

**价值**：扫一眼就知道整个交付推进到哪一步、卡在哪里、哪里需要人介入。流程感知提升最大的单项优化。

## 🟠 中优先级（P1）

### 3. 左侧 Run 列表：信息密度 + 筛选

**现状问题**：
- `.harness-run-item` 条目只有标题 + 状态 + Run ID + 时间
- 没有筛选/搜索能力，Run 多了之后很难定位
- 时间是绝对时间（`fmtTime` 输出），没有相对时间
- 排序规则不明确（看起来按创建时间，但用户更关心最近活跃）

**建议方案**：
- 顶部加**状态筛选芯片**（`el-checkbox-group` 或 `el-radio-group` 按钮样式）：全部 / 进行中 / 待审批 / 已完成 / 失败
- 条目增加**当前阶段小图标**（四色小圆点），扫一眼就知道卡在了哪一步
- 增加**搜索框**（按标题 / Run ID 过滤）——可折叠，默认只显示筛选芯片
- 时间改成**相对时间**（"2 小时前"），hover 显示绝对时间（用 `title` 属性）
- 按 `updatedAt` 倒序，最近活跃的排最上面

**涉及文件**：`admin/harness.html`（列表区结构）、`css/admin.css`（条目样式微调）、`js/admin/pages/harness.js`（筛选/搜索/相对时间逻辑）

**改动量**：小

**价值**：Run 数量上来后刚需，定位成本从 O(n) 降到 O(1)。

---

### 4. 对话体验：消息气泡 + Artifact 卡片化 + Markdown

**现状问题**：
- 对话消息用 `<pre>` 纯文本渲染，左右对齐区分角色，但视觉差异不够
- `artifactType` 只在消息头部显示一个小 Tag，内容还是纯文本 `<pre>`
- "Codex 正在执行"状态只有一个跳动的点 + 固定文案，不知道当前在做什么
- 没有 Markdown 渲染，长文可读性差

**建议方案**：
- **消息气泡化**：用户消息右对齐 + 蓝色背景气泡，Codex 消息左对齐 + 白色/灰色背景气泡（与主站 chat 视觉一致）
- **Artifact 消息特殊渲染**：标记了 `artifactType` 的消息（REQUIREMENT / DESIGN_DOC / IMPLEMENTATION_SUMMARY 等）改成**卡片样式**：
  - 顶部：图标 + Artifact 类型 + 版本号
  - 主体：可折叠的内容区（默认展开，内容支持 Markdown）
  - 底部：Hash + 下载链接
- **执行中状态增强**：根据阶段显示不同的提示文案——
  - 启动阶段初期："正在读取上下文并装配 Prompt..."
  - 有中间事件时："正在分析需求 / 生成方案 / 编写代码..."（从 runtime 事件或阶段名推断）
  - 用动态进度条或多步骤指示替代单点跳动
- **Markdown 渲染**：接入 `marked` 或 `markdown-it` CDN，对消息内容做基础 Markdown 渲染（标题、列表、代码块）。代码块保留 `<pre>` + 语法高亮可选

**涉及文件**：`admin/harness.html`（消息模板 + CDN 引入）、`css/admin.css`（气泡 + Artifact 卡片样式）、`js/admin/pages/harness.js`（消息渲染逻辑）

**改动量**：中

**价值**：日常使用频率最高的区域，直接影响协作体验。

## 🟡 低优先级（P2）

### 5. 新建 Run 的引导式体验

**现状问题**：
- 新建 Run 就是 4 个字段的表单（标题 / 工作目录 / Runtime / 环境 / 原始需求），新用户不知道该填什么
- 工作目录是纯文本输入，容易拼错
- 原始需求没有格式提示

**建议方案**：
- **原始需求**输入框上方加**模板按钮**（如「插入需求模板」），一键填入结构化模板（背景/目标/验收标准/范围）
- **工作目录**改成 `el-autocomplete` 或下拉选择 + 手动输入的组合（从历史 Run 的工作目录中联想）
- 增加**「从会话导入」**按钮：选择一个 chat session，自动把最后一条用户消息作为原始需求（MVP 可以先不做，复杂度较高）
- 需求输入框下方加轻量提示文案（「建议包含背景、目标、验收标准」）

**涉及文件**：`admin/harness.html`（创建对话框结构）、`js/admin/pages/harness.js`（模板逻辑 + 自动补全）

**改动量**：小

**价值**：降低首次使用门槛，属于一次性体验优化。

---

### 6. 视觉调性统一

**现状问题**：
- 状态标签混用英文枚举（`WAITING_APPROVAL`）和中文（「干净」「已有脏改动」）
- 顶部安全边界 Alert 太抢眼（`type="info"` + `show-icon`），作为常驻信息不该每次都抢视觉焦点
- 没有暗色模式适配

**建议方案**：
- **状态标签统一中文语义**：`WAITING_APPROVAL` → "待审批"、`WAITING_INPUT` → "待补充"、`INVALIDATED` → "已失效"、`PASSED` → "已通过"、`FAILED` → "失败"、`RUNNING` → "运行中"、`PENDING` → "未开始"。英文状态码放在 tooltip 里（技术用户需要精确匹配日志时可查）
- **顶部安全边界 Alert 低调化**：改成更浅的底色（或纯文字 + 折叠），只保留 icon + 一行标题，描述折叠
- **响应式中间断点**：900px 处加 2 列阶段卡片的中间断点（目前只有 768px 的 mobile 断点，平板尺寸下 4 列偏挤）
- **暗色模式**（远期）：如果管理后台有暗色模式计划，Harness 页面的哈希值、代码块、pre 背景色需要调整

**涉及文件**：`admin/harness.html`（状态文案）、`css/admin.css`（Alert 样式 + 断点）、`js/admin/pages/harness.js`（`stageMeta` 增加中文 label）

**改动量**：小

**价值**：专业感提升，属于打磨项。

## 落地顺序建议

| 顺序 | 项目 | 优先级 | 改动量 | 价值 | 前置依赖 |
|------|------|--------|--------|------|----------|
| 1 | 工作区与审计层分离 | P0 | 中 | 最高 | 无 |
| 2 | 四阶段 Stepper 可视化 | P0 | 中 | 高 | 无 |
| 3 | 对话体验优化（气泡 + Markdown + Artifact 卡片） | P1 | 中 | 高 | 无 |
| 4 | Run 列表筛选与信息增强 | P1 | 小 | 中 | 无 |
| 5 | 视觉调性统一 | P2 | 小 | 中 | 无 |
| 6 | 新建 Run 引导体验 | P2 | 小 | 低 | 无 |
| 7 | 微交互细节 | P3 | 小 | 低 | 无 |

> **建议先做 1 + 2**：这两项是信息架构层面的核心优化，做完后再根据真实使用反馈决定后续优先级。
> 3（对话体验）虽然是 P1，但可以和 1 并行推进——工作区分离后对话区的展示空间反而更大，优化效果更好。

## 不建议做的（反模式记录）

1. **不要在阶段卡片上加"跳过"按钮**：Harness 的核心价值是阶段门禁，跳过会破坏受控交付模型。真要跳过应该走管理员 override 流程。
2. **不要把 5 个 Tab 全塞到页面主视图**：审计信息的价值是"出问题时能查到"，而不是"每时每刻都显示"。默认收起 + 可展开是正确方向。
3. **不要为了"好看"把状态信息精简到只剩颜色**：色盲用户（约 8% 男性）无法只靠颜色区分状态，必须有形状/图标作为冗余编码。Stepper 方案里的 ✓ / ◷ / ? / ✗ / ╱ 就是为了这个。
4. **不要把能力快照表单做成真正可编辑**：能力快照的本质是"系统解析 + 管理员确认"，不是"用户自由配置"。如果开放自由编辑，等于绕过了 Prompt Pack 的版本管控，这是安全模型的倒退。
